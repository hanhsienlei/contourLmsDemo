# Mini-LMS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a small LMS where students book and manage their own consultations and admins see every consultation, read-only, inside a 5-hour build budget.

**Architecture:**
- The browser talks only to Next.js route handlers (`app/api/**`).
- Handlers check same-origin, verify the session, check the role, validate input with zod, then call a TypeScript `ConsultationService`.
- The service holds every permission and business rule. It talks to Postgres through a server-only Supabase client that uses the secret key.
- Postgres has RLS on with no policies and no grants for anon or authenticated, so the auto-generated API is closed to everyone but the server. The database keeps only data-integrity constraints.

**Tech Stack:**
- Next.js (whatever `with-supabase` installs, 15 or 16) with the App Router, TypeScript
- `@supabase/supabase-js`, `@supabase/ssr`, and the Supabase CLI (local Docker)
- zod, react-hook-form, date-fns, shadcn/ui (with sonner toasts)
- Vitest, `pg` (for tests only), `tsx`

**Spec:** `docs/superpowers/specs/2026-11-22-mini-lms-design.md`. Read it before starting. Section references like §8a point there.

## Global Constraints

- Prefer API route handlers. **No Server Actions** for app features; the template's own auth code may stay as it is.
- **Secret key:** env `SUPABASE_SECRET_KEY`.
  - It is only ever imported in `lib/supabase/admin.ts`, which starts with `import 'server-only'`.
  - It never gets a `NEXT_PUBLIC_` prefix.
  - Only `lib/consultations/service.ts`, `lib/auth/roles.ts`, `scripts/seed.ts` and tests may import `createAdminClient`.
- **Public env vars** follow the installed template (expected: `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`). Use the same names in code, `.env.example` and the README.
- **Booking window:** `MIN_LEAD_HOURS = 24` and `MAX_AHEAD_DAYS = 14`, rolling from now. `SLOT_MINUTES = 15`. All three live in `lib/consultations/rules.ts`, and nothing hard-codes them anywhere else.
- **Text lengths after trimming:** `first_name` and `last_name` 1–100 characters, `reason` 1–1000.
- **Status values:** `scheduled`, `completed`, `cancelled`. Roles: `student`, `admin`. One role per user. Admins don't book.
- **Error body:** `{ "error": { "code": ApiErrorCode, "message": string } }`.

| Code | HTTP status |
|---|---|
| `validation` | 400 |
| `unauthenticated` | 401 |
| `forbidden` | 403 |
| `not_found` | 404 |
| `conflict` | 409 |
| `internal` | 500 |

- **Not-owned rows return 404**, never 403.
- **Raw database errors are never sent to the client.**
- **Sessions are verified on the server with `getClaims()` or `getUser()`**, never `getSession()`.
- **Admin list `limit`:** default 20, at most 100.
- **Commits:** small, with Conventional Commit style messages. Every commit message ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- **Never commit** `.env.local` or `requirement.txt`. Both are already in `.gitignore`.
- **Frontend:** shadcn/ui components. Before Tasks 10–12, check the available skills for a frontend-design skill and use it. Run `design:accessibility-review` on the finished UI in Task 12. Components hold no business rules; the only checks in them are form validation for UX.

## Review Focus

1. **Time zones and daylight saving.** A student in Melbourne opens the picker over a daylight-saving change. Every slot offered must be a real, 15-minute-aligned instant inside the window, with no duplicates or gaps. *Test in Task 4:* `availableSlots` across the window has every element aligned, strictly increasing, and the first and last inside the window.
2. **A form left open too long.** A slot that was valid when chosen is now less than 24 hours away. The server must refuse it with a clear 400, and the UI shows the message. *Test in Task 7:* `book` at `now + 24h - 1 minute` (aligned) throws `validation`.
3. **Double-clicking "Book".** Two simultaneous bookings of the same slot must give exactly one success and one 409, never two rows. *Test in Task 7:* two parallel `book` calls with `Promise.allSettled` give one fulfilled and one `conflict`. The UI also disables the submit button while a request is pending (Task 11).
4. **Ties in the admin list.** Several students booked the same time. Keyset pagination must return each row exactly once, across pages. *Test in Task 7:* 3 rows at the same `scheduled_at` with `limit: 2` give 2 rows and then 1, with no duplicates.
5. **A tampered pagination cursor** (not valid base64 JSON, or a non-UUID id). It must give 400 and never reach PostgREST. *Test in Task 4:* `decodeCursor('garbage')` and a cursor holding `id: "x),or(1.eq.1"` both throw a ZodError (or return null, which the route maps to 400).

  scheduledAt: string; status: ConsultationStatus; createdAt: string; updatedAt: string };

**Behaviour (spec §8 and §8a):**
- **Columns are written by name.** `user_id` always comes from the `userId` argument.
- **Booking window:** `book` and `reschedule` throw `errors.validation('Consultations must be booked between 24 hours and 14 days ahead')` when `!isWithinBookingWindow`.
- **Every status change is one conditional update.** It's scoped by `id`, `user_id` and the source status, and uses `.select().maybeSingle()`:
  - `reschedule`: only from `scheduled`.
  - `cancel`: only from `scheduled`, setting `cancelled`.
  - `setCompleted(true)`: `scheduled` → `completed`. `setCompleted(false)`: `completed` → `scheduled`.
- **If no row changed**, read the row once with `id` and `user_id`:
  - missing → `errors.notFound()`
  - status `cancelled` → `errors.conflict('Cancelled consultations cannot be changed')`
  - already in the target state, for `setCompleted` only → return it (an idempotent no-op)
  - anything else → `errors.conflict('Only scheduled consultations can be rescheduled or cancelled')`
- **Database errors go through `mapDbError`.**
- **`listAll`** selects `..., profiles(email)` and orders by `scheduled_at` then `id`, both ascending. It fetches `limit + 1` rows to tell whether there's a next page.
  - With a cursor, it uses `.or(\`scheduled_at.gt."${iso}",and(scheduled_at.eq."${iso}",id.gt.${uuid}))\``. `iso` is `new Date(cursor.scheduledAt).toISOString()` and `uuid` is the id that passed `z.uuid()`. This is the **only** `.or()` in the codebase. Add a comment explaining why it's safe: the values are re-serialised from strictly validated data, never raw input (spec §8a, rule 1).
- **Map rows to camelCase** in one `toConsultation(row)` helper.
